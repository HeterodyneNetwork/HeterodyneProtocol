# Heterodyne 0.5.0 Family Review - 2026-07-30

Reviewer: GLM-5.2
Scope: the four 0.5.0 normative documents (`docs/spec/heterodyne-{core,comms,control,social}.md`),
the non-normative family map, the 36 ADRs in `docs/adr/`, the registry, the prepared
release manifests, the threat model, and the normative conformance-vector corpus plus its
TypeScript generator.
Status of review: non-normative analysis.

Method: direct read of all four specs and the threat model; targeted verification of each
high-severity item against source with `grep` and direct file reads; code/registry/vectors
swept with the semble search tool and three parallel research passes (ADRs, registry
versioning, vectors/generator). Findings marked **(verified)** were checked directly by the
reviewer; **(reported)** are from the parallel passes with file:line evidence and were not
re-derived line by line.

Baseline gate: `npm --prefix docs/spec/vectors/generator run family:check` passes (DAG,
registry digest, family prose all validate). The full generator `check` (337 tests / 317
vectors) was reported passing by the parallel pass; the reviewer ran only the offline
family gate. The findings below concern gaps and inconsistencies those gates are **not
designed** to catch.

Severity legend: **High** = wrong/contradictory normative bytes or a security property not
delivered. **Medium** = real inconsistency or coverage hole that could mislead an
implementer. **Low** = editorial, hygiene, or acknowledged-residual.

---

## 1. Executive summary

This is a mature, unusually disciplined 0.x specification. The KERI-anchored identity
model, the dual-proof NID delegation, the byte-exact wire-conformance posture, the
registry-allocated stamping/profile system, and the claim ledger + OIDC/JWT projection with
a Radicle continuity mirror are internally coherent and well-defended. The threat model is
explicit about what it does and does not promise (metadata leakage, no erasure, not
post-quantum, honest-client assumption). Control is honestly gated as incomplete.

The highest-value problems are **not** in the prose security design. They are:

1. **The reference verification corpus encodes events that do not match the 0.5.0 stamping
   rules** (inception/root/delegation fixtures omit the mandatory `spec_version` tag), so
   the "accepted KEL head" every `kel_head` vector references is computed over a
   legacy-inferable form. (Medium, verified)
2. **Two Accepted ADRs (017, 023) and the generator still carry `room_secret` /
   `private_broadcast` machinery that the 0.5.0 specs silently dropped**, with no
   supersession marking. (Medium, verified)
3. **Several large normative behaviors have thin or no byte-exact vector coverage** -
   the Comms §8.1 credential-sync authorization ledger, the Social §8 ATProto binding, and
   the `deny-until-repo` hard-reject path. (Medium)
4. **Two Accepted ADRs (035, 036) postdate the specs and are unintegrated**, including an
   agent-authorship/OIDC-workload-token design whose only acknowledged control is
   attribution, not prevention. (Medium, security-adjacent)

No catastrophic protocol-level flaw was found. The recommendations below are about closing
the gap between a rigorous prose spec and a reference corpus/generator that fully reflects
it.

## 2. Strengths

- Clean, downward-only document DAG (`Core <- Comms <- {Control, Social}`) with
  independent per-document versioning and byte-exact conformance semantics.
- Strong identity core: KERI cold root + epoch keys, witness-threshold rotations with
  first-seen fork handling, backdated-compromise windows, and `nip01_raw`-preserving
  verification that blocks reserialization/signature-confusion attacks.
- Dual-proof NID delegation (epoch BIP-340 + Ed25519 `nid_proof` over the same binding)
  correctly separates Nostr authorship from Radicle ref authority.
- Honest privacy-tier framing: Tier 2 is explicitly "plaintext on every allowed seeder"
  with mandated UI honesty; Tier 3 is encrypted-at-rest-before-commit with blind carriers.
- Claim ledger + OIDC/JWT projection with simultaneous HTTPS/Radicle byte-identical
  continuity, writer-namespaced status lists, and receiver-verifiable MLS migration.
- Threat model (`docs/security/threat-model.md`) explicitly enumerates actors, residual
  metadata risk, non-erasure, the not-post-quantum caveat, and pre-1.0 work.
- Control is correctly gated: its conformance claim is closed and its reserved strict
  profile is inactive until ADR-030 integration and a minimum vector corpus land.

## 3. Security findings

### S1 - Cold root is a single point of failure for the npub->RID binding [Medium, verified]
`docs/spec/heterodyne-core.md:620-636` (`core-identity-pointer`): the canonical npub-to-RID
binding and any changed-RID re-anchor are **always cold-root-signed**. There is no witness
threshold on the pointer or the re-anchor, unlike KEL `none`-rotations which can be
witness-gated (`core.md:312-350`). Cold-root compromise therefore lets an attacker redirect
the persona's RID until a re-anchor; the threat model calls cold-root compromise
"catastrophic persona authority until KERI recovery/re-anchor" (`threat-model.md:149`).
This is inherent to the KERI cold-root design and is acknowledged, but it is the single
highest-blast-radius trust assumption in the family.

**Suggestion:** optionally allow a witness-threshold co-signed re-anchor pointer, reusing
the `none`-rotation receipt machinery, so a deployment that wants to bound cold-root blast
radius can require witness attestation before a new RID binds. This adds a knob without
weakening the default cold-root-authoritative path.

### S2 - Agent authorship (ADR-036) is Accepted but unintegrated, and its only control is attribution [Medium, verified + reported]
`docs/adr/2026-07-30-036-agent-authorship-oidc-workload-tokens-and-moderation.md` is dated
and Accepted (2026-07-30), two days after the specs. It defines agent authorship, OIDC
workload tokens, and a `kind:31001` agent-signing profile at `d=agent:<role-id>`
(`ADR-036:112-124,336`), and states "Registry revision 2 remains immutable. Integration
creates revision 3." But `docs/spec/registry/manifest.json` is still revision 2,
`docs/spec/vectors/generator/src/{registry,stamping}.ts` contain no agent profile (semble
confirms only the control `session-device` profile is tested), and
`docs/spec/heterodyne-control.md` still only "reserves" agentic semantics (`control.md:40-52`).
ADR-036 itself discloses the residual risk that a compromised/non-conformant full node can
still sign mislabeled agent content, and that the required Control "automated agents"
mitigation section does not yet exist (`ADR-036:363-365,430-432`).

**Impact:** until integrated, attribution/audit/reporting is the only control over agent
content, and an implementer following the Accepted ADR today produces `d=agent:<role-id>`
`kind:31001` events that Core §6.1 and registry rev 2 do not recognize as conformant.
**Suggestion:** either land rev 3 + Control spec text + the agent vectors, or annotate
ADR-035/036 "Accepted, integration pending" so the 0.5.0 specs remain the unambiguous
authority during the window.

### S3 - No explicit bound on double-ratchet message-key deletion latency [Low-Medium, verified]
`docs/spec/heterodyne-comms.md:537-540` mandates deleting the consumed message key after
ratchet advancement, but forward secrecy and post-compromise security depend on *prompt*
deletion (`threat-model.md:126-127,239-243`). There is no normative ordering constraint
tying deletion to acceptance of the next message key. **Suggestion:** add a non-normative
or SHOULD-level requirement that a receiver delete a consumed message key before deriving
the next, so FS is not silently weakened by an implementation that batches deletions.

### S4 - Threshold-0 / no-witness `none`-rotations let a compromised epoch key keep continuity [Low, verified]
`core.md:312-350`: a `none`-strategy rotation needs the prior epoch-key signature plus the
witness threshold; with threshold 0 and no witnesses, a compromised epoch key can rotate
continuity to an attacker-controlled key without the cold root. Recovery is cold-root
re-anchor only. This is inherent to KERI and acknowledged, but it is not surfaced in the
threat model as a deployment-relevant choice. **Suggestion:** add a line in
`threat-model.md` advising operators that witness-free personas offer no continuity
protection against epoch-key compromise.

## 4. Inconsistency findings

### I1 - Generator fixtures omit the mandatory `spec_version` stamp, so the accepted KEL head is over a legacy-inferable event [Medium, verified]
`docs/spec/vectors/generator/src/kel.ts:15-33` (`inceptionTemplate`) and
`docs/spec/vectors/generator/src/topics-keri-authority.ts:117-147` (root W9, delegation W10)
build the fixture key-material events **without** a `spec_version` tag. Core §3.2 rule 2
(`core.md:135-139`) requires `['spec_version','<owner>/<semver>']` on any Heterodyne-allocated
kind whose content is empty or non-JSON, and the inception/delegation examples at
`core.md:288-306,479-498` include it. Per the closed legacy-inference table
(`core.md:163-179`), an absent stamp on a Core kind MAY select the monolith/0.4.0 schema.
Therefore every `kel_head` in the `keri-authority/` corpus (which references
`head.id` computed over this inception, e.g. `topics-keri-authority.ts:25`) points at an
event that, under the 0.5.0 rules, is legacy-inferable rather than a clean 0.5.0-stamped
event. **Suggestion:** add the stamps and recompute the affected event ids / `kel_head`
values (this propagates into the materialized-KEL vectors and the keri-authority set).

### I2 - keri-authority/006 rotation fixture carries invalid `content: "[]"` [Low-Medium, verified]
`topics-keri-authority.ts:92` sets the forbidden-on-rotation fixture's `content` to `"[]"`,
but Core §4.3 (`core.md:337-344`) mandates the byte form
`{"spec_version":"core/0.5.0","receipts":[...]}`. The vector is intended to be rejected for
`kel_head_forbidden`; the verdict is unaffected, but a verifier that validates the rotation
content schema before classifying the `kel_head`-forbidden case (Core §9 step 1 / §4.4 step
3) would reject for a *content* reason first, so the expected `reason_code: kel_head_forbidden`
may not match a conformant check ordering. (The same `"[]"` form also feeds the
materialized-KEL fixture in `topics-keri-authority-c.ts`, per the reported pass.)
**Suggestion:** give the fixture the valid rotation content and let only the forbidden
`kel_head` trigger the reject.

### I3 - Normative vectors use reason strings absent from the registry [Medium, verified]
`docs/spec/vectors/generator/src/topics-keri-authority-b.ts:84,87,101` emit `repo_unreachable`
and `repo_causally_behind` as `normalized.reason` into vectors 017/018; neither string exists
in `docs/spec/registry/reason-codes.json` (only `provisional_not_final` is present there).
Core §9 step 7 returns "a closed registry reason code" and §14 (`core.md:1204`) requires
"the verdict and reason code MUST equal the expected values exactly." Whether these are
rejection reason codes or descriptive `normalized.reason` fields is ambiguous; either way
they sit outside the closed vocabulary the specs describe. **Suggestion:** register both
slugs (owner `core`) or re-point the vectors, and have Core §9 state explicitly whether
`normalized.reason` is constrained to registry vocabulary.

### I4 - Stale `room_secret` / `private_broadcast` machinery in generator, fixtures, and ADRs [Medium, verified]
The 0.5.0 specs dropped the room-secret mechanism: Comms makes the audience key the sole
Tier-3 delivery path and rejects `room_key.v1` (`comms.md:100-145,214`), and Social retires
the broadcast/discussion room kinds - new rooms use only `identity_room`, `config_room`,
`public_discussion`, `private_discussion` (`social.md:1106-1110`). Yet the generator still
encodes the old model: `docs/spec/vectors/generator/src/topics.ts:332,517,537,564,602,742-743,
893,913,923,943` and `fixtures.ts:129,132-133`, plus the committed `fixtures.json:208-212`
(`room_secrets`, `alice_private_broadcast_v1`, `heterodyne.room_secret_wrap.v1`,
`public_broadcast`/`private_broadcast` room kinds). ADR-017 (broadcast taxonomy) is still
"Accepted" with no supersession note, and ADR-023 (room_secret) is still "Accepted"; ADR-029
recast the relevant monolith sections but expressed supersession at the section level, not
the ADR level.

**Suggestion:** mark ADR-017 and ADR-023 superseded (following the model ADR-005 already uses
for its supersession-by-ADR-023 note), correct ADR-029's stale "Matrix room-secret optional
alternative" row, and remove the `room_secret`/`private_broadcast` data from the generator
and `fixtures.json` (this rework is already mandated by ADR-033 reqs 37-39).

### I5 - Supersession of older ADRs is section-level, not ADR-level [Low-Medium, reported]
ADR-029's supersession table (`docs/adr/2026-07-01-029-...md:104-116`) recasts the monolith
sections where ADR-009, ADR-017, ADR-020, and ADR-023 landed, but none of those four ADRs
carries a "Superseded by ADR-029" line. This is the root cause of I4: an implementer reading
ADR-017 or ADR-023 in isolation would build non-conformant room kinds. **Suggestion:** add
explicit `Superseded by` lines (contrast ADR-005 and ADR-027, which are marked correctly).

### I6 - Older ADRs cite renamed anchors and retired invariant labels [Low, reported]
ADRs 001-016 and 019-027 cite the monolith `docs/spec/heterodyne.md` and bare section
anchors (now split/renamed) and the retired bare invariant labels I1-I7, which ADR-033 req
33 namespaced into `CORE-I-*`/`COMMS-I-*`/`CONTROL-I-*`/`SOCIAL-I-*`. Links are recoverable
via `docs/spec/archive/heterodyne-0.4.0-anchor-map.md`, but the ADRs were not re-qualified
to the `heterodyne:<doc>/<version>#<anchor>` form ADR-033 req 34 mandates for normative
references. Low severity; editorial.

### I7 - Reference verification logic diverges from spec in the generator [Low-Medium, reported]
The generator is non-normative tooling (`core.md:1216`), but implementers use it as the
reference. Three reported divergences:
- **Claim attenuation is too strict.** `claims.ts:489-494` rejects a delegated chain whose
  child preserves (rather than strictly narrows) both time bounds, but Comms §10.2
  (`comms.md:1022-1025`) permits "preserve or narrow." The code rejects a spec-permitted
  delegation, leaving the preserve case untested.
- **ID-token verifier accepts an empty nonce.** `oidc.ts:570` is satisfied by `"" === ""`,
  but Comms §12.2 (`comms.md:1232-1234`) requires a non-empty nonce. The minter enforces
  non-empty (`oidc.ts:647`); the verifier does not, so a forged token with an empty nonce
  would pass the reference verifier.
- **Claim-verification stage ordering differs.** `claims.ts:345-439` applies local trust
  policy last, while Comms §10.1 (`comms.md:990-997`) lists it at stage 5 - so a claim that
  is both untrusted and revoked resolves to `revoked` in code but `untrusted` under the spec
  ordering.

**Suggestion:** reconcile the reference verifier with the spec text (or add explicit
coverage that forces the divergence into the open), since an implementer copying it
inherits the wrong behavior.

## 5. Gap and coverage findings

### G1 - Control profile remains the largest unfinished area [Medium, verified]
`docs/spec/heterodyne-control.md:274-296` keeps the Control conformance gate closed on
`adr-030-accepted`, `adr-030-integrated`, and `minimum-control-vectors`. Section 5
(`control.md:186-204`) enumerates what is missing: enrollment bootstrap/finality/revocation,
closed RPC request/response/replay schemas, grant tiers and object-level authorization,
single-use enrollment tokens, MCP JSON-RPC lifecycle with default-deny inbound execution,
encrypted audit semantics, and the minimum vector corpus. This is honest and well-gated, but
it is the family's biggest open item and blocks the entire agentic/RPC surface (including
the S2 agent-authorship control).

### G2 - Comms §8.1 credential-sync authorization ledger has no byte-exact vectors [Medium, verified]
`comms.md:614-763` defines an elaborate authorization record: a closed canonical compact-JSON
schema, a domain-separated SHA-256 signature prefix, `valid_until`/zero-sentinel semantics,
a fully specified 5-tuple canonical ordering, an absorbing-revocation resolver, and ledger
continuity across config-key rotation with atomic predecessor/successor digests. The only
coverage is a structural `CredentialRecordProbe` in `docs-lint.test.ts:999`; there are no
dedicated consumer/producer vectors exercising the signature prefix, the 5-tuple ordering,
or the rotation continuity check. The `acceptance-gating/credential-*` vectors only model the
§8 hook verdict, not the §8.1 ledger. **Suggestion:** add a focused vector subset for §8.1.

### G3 - Social §8 ATProto and several Social anchors lack vector coverage [Medium, reported]
Social §8 (`social.md:678-842`) carries normative MUSTs - SSRF rejection of RFC 1918/loopback
(`691-702`), one-sided-rejection bidirectional binding (`722-724`), PDS-record-first ordered
verification (`735-741`), and unilateral revocation (`780-788`) - but no vector references
`social-atproto*`. ATProto is OPTIONAL, so this binds only ATProto-claiming implementations.
Additionally, the corpus's single `spec_refs` slot never references `social-mixed-tier-fanout`,
`social-discovery`, `social-sets`, `social-revocation`, or `social-labels`, and the
cross-persona vectors point at `social-interactions` instead of `social-cross-persona`
(`social.md:163-192`), so traceability for those sections is broken. **Suggestion:** add
ATProto vectors and fix the cross-persona anchor.

### G4 - The `deny-until-repo` hard-reject path has no vector [Medium, reported]
Core §9 (`core.md:820-825`) says under `deny-until-repo` the verifier "MUST return `reject`
with reason `provisional_not_final`." The corpus only models `provisional-accept`
(e.g. `keri-authority/017`); no vector exercises the policy that must hard-reject, and
`provisional_not_final` is registered but unused. **Suggestion:** add a `deny-until-repo`
reject vector.

### G5 - Most vectors pin registry revision 1 while docs pin revision 2 [Low, verified]
~262 vectors carry `registry_revision: 1` while the specs and all four release manifests pin
revision 2 (`registry/manifest.json`, `core.md:88`). This is deliberate
(`generator/src/vector-metadata.ts:409-410` pins only the newer topics to 2; `history/1.json`
is preserved so both resolve) and tolerated by the schema. **Suggestion:** add a one-line note
in Core §14 so a strict reader does not read the revision-1 corpus as staleness.

### G6 - Root-attestation +/-300s freshness is untestable as authored [Low, reported]
Core §6 (`core.md:470-472`) makes the +/-300s rule kind:31000-specific and normative, but the
`keri-authority/*.json` vectors pin no verifier clock; vector 009 uses `created_at` T+340 with
expected `accept`, which cannot distinguish accept from reject without a pinned
`evaluation_time`. **Suggestion:** pin a simulated clock on freshness-sensitive vectors.

### G7 - `nip01_raw`-first verification is not modeled as a rejection case [Low, reported]
Core §3.1 (`core.md:122-126`) requires a verifier to hash `nip01_raw` rather than reconstruct
the signing input. The generator's `verifyEventSignature` recomputes the id from parsed
fields (`nostr.ts`), and no consume vector exercises a `nip01_raw` that diverges from the
canonical serialization of the parsed event. **Suggestion:** add a consume vector that
mutates `nip01_raw` independent of the parsed fields.

### G8 - `verify.ts` does not re-check expected verdicts [Low, reported]
`verify.ts` validates JSON schema and that regenerated bytes equal committed bytes, but does
not re-run semantic verification against `expected_output.verdict`/`reason_code`. A wrong
expected verdict survives unless a vitest case happens to assert it. **Suggestion:** add a
verdict-replay check or a lint that every normative vector's expected output is asserted by
at least one test.

### G9 - Registry hygiene: kind:22242 unregistered; 10001/10003/10004 uncited [Low, reported]
Core §10.4 makes `kind:22242` (NIP-42 AUTH) normative (`core.md:971`) but it is absent from
`kinds.json`, while many other unprofiled upstream kinds are registered. Separately, kinds
`10001`, `10003`, `10004` are registered (`kinds.json`) but referenced nowhere - dead
allocations covered only by the broad `10000-10999` range. **Suggestion:** register 22242 (or
document why pure NIP-42 is out of scope) and prune or cite the unused list kinds.

### G10 - Minor registry/manifest inconsistencies [Low, reported]
- Reason-code naming is split between underscore and hyphen separators across
  `reason-codes.json` (42 underscore vs 33 hyphen); both pass the schema regex.
- `double-ratchet` feature attribution diverges: Comms prose treats it as a Comms feature
  (`comms.md:1468`) but the Comms release manifest never enumerates it and the manifest
  schema only surfaces it under Control (`release-manifest.schema.json:71,80`).
- Control's "Normative dependencies" header lists only Comms (`control.md:13`) while its
  release manifest must declare Core+Comms; Social lists both. Defensible if "dependencies"
  means direct-only, but the asymmetry could be explicit.

## 6. Prioritized recommendations

1. **Fix the corpus's KEL fixtures (I1, I2).** Add the mandatory `spec_version` stamps to
   the generator inception/root/delegation fixtures and recompute the affected `kel_head`
   ids; give the rotation fixture valid content. This is the cleanest correctness fix and
   propagates into the materialized-KEL vectors.
2. **Retire `room_secret`/`private_broadcast` cleanly (I4, I5).** Mark ADR-017/023
   superseded, fix ADR-029's stale row, and strip the stale data from the generator and
   `fixtures.json` (already mandated by ADR-033 reqs 37-39).
3. **Close the reason-code vocabulary gap (I3).** Register `repo_unreachable` /
   `repo_causally_behind` (or re-point the vectors) and clarify in Core §9 whether
   `normalized.reason` is registry vocabulary.
4. **Decide ADR-035/036 integration (S2, G1).** Either land registry rev 3 + Control spec
   text + agent vectors, or annotate the ADRs "Accepted, integration pending" so the specs
   remain the unambiguous authority during the window.
5. **Close the highest-value coverage holes (G2, G4, G6, G3).** Add vectors for the §8.1
   credential-sync ledger, the `deny-until-repo` hard-reject path, clock-pinned root
   freshness, and the Social §8 ATProto MUSTs.
6. **Reconcile the reference verifier with the spec (I7).** Fix the empty-nonce acceptance,
   the over-strict attenuation, and the trust-policy ordering so the generator is not a
   source of incorrect guidance.
7. **Add an optional witness-threshold re-anchor (S1).** Reuse the `none`-rotation receipt
   machinery to let deployments bound cold-root-compromise blast radius without weakening
   the default cold-root-authoritative path.

## 7. Items checked and found sound (to avoid re-litigation)

- Document DAG, registry revision/digest consistency, and the legacy owner-inference table
  (`core.md:163-179`) match `kinds.json` byte-for-byte; `family:check` passes.
- All 28 security-invariant IDs are defined and cited; strict-profile flattened memberships
  in core §12.2, comms §15.1, social §13.1, and control §6.1 are exact supersets of their
  prerequisites.
- `kind:31006` is correctly "reserved, not eligible"; no ADR allocated it.
- ADR-034 (claims/ledger/OIDC/status) is fully integrated in Comms and the registry; the
  threat-model acceptance-evidence table (§7) traces each criterion to anchors, registry,
  and vectors.
- MLS migration (ADR-012 / Social §12.2) - 60s drain, intent/ack/abort, receiver-verifiable
  flip, forbidden rollback - is consistent; the "Matrix MLS not finalized" caveat is carried
  forward.
- Control coverage is honestly marked incomplete (`coverage.ts` hardcodes the
  `incomplete-draft` status); the single inactive profile
  (`heterodyne-control-session-device-v1`) has its covering vector.
- v050-suffixed vectors meaningfully differ from non-v050 counterparts (re-stamp + recompute
  id/sig + assert 0.5.0 form), not near-duplicates.
