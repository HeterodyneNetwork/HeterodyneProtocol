## Context

Three whole-repository reviews dated 2026-07-30 evaluated commit `e02bdee`.
Current main is `07e46d7`, which already integrates ADR-035, ADR-036, and
registry revision 3. The reviews therefore mix current defects, stale
observations, optional extensions, and claims contradicted by existing
vectors.

The accurate findings reveal four root causes:

1. pre-0.5 fixture helpers survived the four-document owner-stamp split;
2. generator regeneration is sometimes the only oracle for generator output;
3. several intended security profiles exist only in non-normative TypeScript;
   and
4. the flat release-manifest feature list cannot express feature ownership or
   prerequisites.

The project is pre-1.0. The user has clarified that behavior and conformance
artifacts remain in flux throughout `0.x`; immutable protocol identifiers and
bytes begin at 1.0. Published `0.x` release records must still preserve their
exact artifact digests.

## Decision

### 1. Correct current 0.x artifacts in place

The current 0.5.0 KEL fixtures and vectors are corrected in place. Inception
retains its canonical timestamp and gains the required Core owner stamp.
Rotation retains its authority-window timestamp and uses the exact compact
object containing `spec_version` and its actual ordered `receipts` array
(empty only when the valid set is empty). Valid competing successors produce
Core's stalled/duplicity state rather than a schema rejection.

Current `0.x` vector IDs and bytes may change when a documented protocol
correction requires it. A published release record continues to identify its
exact corpus by digest; archived historical bytes are not silently
restamped. Protocol-level immutability begins at 1.0.

### 2. Make KEL conformance executable

The KEL corpus gains an independent exact-byte parser and replayer. It verifies
raw event bytes, signatures, sequence, prior digest, controller authority,
witness receipts, threshold, fork, stall, and materialized state. A generator
cannot establish conformance merely by reproducing its own output.

All current KEL vectors either execute that replayer or declare a non-wire
evidence class that cannot be cited as byte-exact conformance.

### 3. Close the witness-free rotation ambiguity

`strategy:none` requires a prior witness threshold of at least one and enough
valid receipts to satisfy it. A witness-free or threshold-zero persona rotates
only with `strategy:committed`. A threshold-zero `strategy:none` event is
rejected before candidate selection and cannot stall a valid committed
successor, though it may be retained as non-authoritative attempted-fork
evidence. Competing valid committed successors stall under the ordinary
duplicity rule.

### 4. Carry the node-advertisement possession snapshot

`kind:31010` carries exactly one canonical `repo_head` tag. The NID proof binds
it with the RID, node, single endpoint, and expiry. The head is the canonical
repository head at issuance and remains a possession snapshot, not a promise
that no later push occurred.

The advertised endpoint must serve an object graph containing that head until
expiry. Missing, malformed, duplicate, mismatched, or unserved heads are
rejected. Transport unavailability is retryable/provisional; rejection as
unserved requires a successful graph fetch proving exclusion.

### 5. Lift security profiles into normative text

Core adopts a closed JWK proof profile and the generator is tightened to match:

- Ed25519/EdDSA;
- P-256/ES256; and
- RSA of at least 2048 bits/RS256.

The public-JWK proof's protected JWS header is the closed object
`{"alg":"<allowed algorithm>"}`. `alg` is its sole member, is required, and
must match the JWK type exactly; every additional protected-header member
rejects.

Each key type permits only its RFC 7638 thumbprint members plus optional
`alg`, `use`, `key_ops`, and `kid`. When present those metadata members must
equal the selected algorithm, `sig`, `["verify"]`, and the recomputed
thumbprint respectively. All other members, `none`, MAC/HS algorithms, `oct`,
wrong curves, weak RSA, and algorithm/type mismatch are rejected.
Conformance includes distinct missing-`alg` and extra-protected-header-member
negative cases.

Comms labels every HKDF input and states how the derived key enters NIP-44. It
also makes Double Ratchet state advancement, persistence, and consumed-key
erasure atomic before plaintext release.

### 6. Correct claims, OIDC, and token-status behavior

Claim and revocation bodies rename `comms_version` to
`spec_version:"comms/0.5.0"`. Their `registry_revision:2` remains the claim
profile's genesis allocation pin.

Attenuation may preserve time bounds while decreasing remaining depth and
preserving or narrowing every authority dimension. An OIDC nonce must be
nonempty on both sides. Claim verification follows ADR-034's order, applying
local trust/release policy only after repository, revocation, and proof
validation.

Status-list producers retain deterministic level-9 ZLIB-wrapped DEFLATE as a
recommended stable encoding. Consumers accept any valid signed
ZLIB-wrapped DEFLATE representation and do not require local recompression to
match.

### 7. Define generalized credential-ledger config-key transitions

Credential state advances through epoch-signed, fully receipted checkpoints.
The checkpoint is one closed record with exactly:

```text
type, persona, generation, sequence, previous_checkpoint,
record_set_digest, node_roster, config_head, config_key_id,
config_key_sha256, pairwise_secret_sha256, exposure_set_sha256,
config_bootstrap_recipients_digest, governed_decrypt_key_bindings_sha256,
historical_decrypt_obligations_sha256,
secret_transition_digest,
generation_transition, epoch_pubkey, kel_head, created_at, epoch_signature
```

`config_head` is the typed Git snapshot immediately before the commit that
stores the checkpoint. The three legal continuity forms are genesis
`(generation=0, sequence=0, previous_checkpoint=null,
generation_transition=null)`, an ordinary same-generation successor naming
the immediately prior sequence's checkpoint, and a new-generation sequence-zero
successor with null predecessor and `generation_transition` naming the exact
staged, independently valid reset candidate that accepts atomically with it.
Every other combination rejects.

Every checkpoint binds the exact authorization-record set, nonempty roster,
config-key and OIDC pairwise-secret commitments, conservative exposure set,
complete signed repository-inventory/retention-snapshot/binding set, complete
historical-decrypt-obligation frontier, applicable bootstrap and
secret-transition records, and the current epoch key and KEL head. Every
roster NID must have an active durable delegation and must receipt the exact
candidate after decrypting and replaying it. Each receipt independently
recomputes the repository-inventory/retention-snapshot/binding object `K(C)`,
governed-ciphertext
set `G(C)`, active-obligation projection `O(C)`, complete maximal frontier
`F(C)`, their exact `G(C) = O(C)` equation,
`governed_decrypt_key_bindings_sha256`, and
`historical_decrypt_obligations_sha256`. A superseded KEL key cannot
backdate a newly accepted checkpoint. Any authorization, source, assignment,
retirement, transition-action, repository-inventory record/ref/scan cut,
retention-snapshot, governed-key-binding, obligation, obligation-provenance,
or governed ciphertext mutation between
the candidate basis and its complete receipt set invalidates the candidate;
revocations remain writable and force reproposal rather than being held.

Every checkpoint also enforces two singleton identities after applying only
its exact accepted-transition projection. Operational `oauth-pairwise`
assignments must resolve to exactly one `(secret_id,instance_commitment)`
tuple, every operational holder source must name it, and its commitment must
equal the checkpoint's `pairwise_secret_sha256`. A null-transition or
exposure-only successor may add a holder only for that same tuple and keeps
the predecessor commitment unchanged. Introducing a different pairwise tuple
requires a non-null transition that includes and atomically retires every
predecessor and competing pairwise assignment and establishes exactly one
successor tuple.

Exactly one operational `epoch` tuple must likewise equal the current Core
KEL `(epoch_pubkey,kel_head.event_id,kel_head.seq)` identity and the
checkpoint's epoch fields. Every operational current-epoch holder source and
assignment must name that same tuple. Noncurrent epoch assignments remain
conservative historical exposure only. A holder may be added for the
unchanged canonical tuple, but a different epoch identity requires the
corresponding cold-root-authorized KEL rotation, transition accounting, and
singleton closure. A null transition or competing source cannot manufacture
another current epoch. These pairwise and epoch checks apply to genesis,
same-key successors, config-key transitions, and emergency reset before any
receipt counts.

At most one nonidentical valid, unaccepted, and unabandoned successor of an
accepted checkpoint may be a candidate. Competing candidates stall
checkpoint advancement and credential-plane authority until one candidate is
established, one exact abandonment becomes canonical, or cold-root reset
starts from the last common fully receipted checkpoint.

Every config-key ID is fresh random 16-byte material encoded as exactly 32
lowercase hexadecimal characters and must decode/re-encode byte-identically
before it enters a path or `refs/heads/enc/<config-key-id>` name. A producer
selects an ID absent from every active or inert signed encrypted ref; candidate
publication is create-only, and any collision burns that ID and requires a
rebuilt candidate.

Generic secret identifiers are class-selected rather than one ambiguous hash
field: `config-audience` uses that exact 32-hex config-key ID, while every
other secret class uses a random 32-byte, 64-hex instance ID. Source,
assignment, transition-action, and successor records preserve that identity.
The checkpoint fields historically named `config_key_sha256` and
`pairwise_secret_sha256` are domain-separated
`heterodyne-node-secret-instance-v1` commitments to the exact secret bytes,
not bare secret hashes; bootstrap plaintexts, transition targets, source
records, and actions must recompute the same commitments.

Every retained ciphertext or pointer profile independently marks the bytes as
an encrypted decrypt dependency. If that authenticated profile does not embed
its exact decrypt-secret tuple, one closed
`heterodyne.governed-decrypt-key-binding.v1` record supplies it:

```text
type, persona, binding_id, retained_ciphertext, secret_class, secret_id,
instance_commitment, issued_at, authority, signature
```

`retained_ciphertext` is the exact closed locator row used by the obligation
below. Its deterministic ID is:

```text
binding_id =
  lowercase_hex(SHA256(
    UTF8("heterodyne-governed-decrypt-key-binding-id-v1") || 0x00 ||
    UTF8(JCS(retained_ciphertext))
  ))
```

The record is stored at:

```text
credential-sync/governed-decrypt-key-bindings/
  <binding-id>/<record-digest>.json
```

The path ID equals the recomputed locator-derived ID and the filename digest
equals lowercase-hex SHA-256 of complete signed JCS. Exact duplicate bytes are
idempotent. Nonidentical otherwise-valid records for
one `(persona,binding_id)` quarantine that ID and reject dependent
obligations/checkpoints rather than selecting by arrival order. `issued_at`
is a JSON-safe nonnegative integer. `authority` is
the exact closed `{signer_type,signer,kel_head}` selected by the governing
class and owner at artifact creation: the exact current epoch for an ordinary
binding or the exact cold-root/reset authority for emergency reconstruction.
Historical signer, KEL ancestry, and compromise-cutoff validation apply. The
selected authority BIP-340-signs:

```text
SHA256(
  UTF8("heterodyne-governed-decrypt-key-binding-v1") || 0x00 ||
  UTF8(JCS(record with signature omitted))
)
```

`signature` is exactly 128 lowercase hexadecimal characters.

The governed repository universe is a signed monotonic protocol record.
`heterodyne.repository-retention-inventory.v1` contains exactly:

```text
type, persona, inventory_sequence, previous_records,
basis_checkpoint_digest, target_generation, target_sequence,
repository_refs, issued_at, epoch_pubkey, kel_head, epoch_signature
```

Genesis uses sequence zero, no parents, null basis, and
`(target_generation=0,target_sequence=0)`.
Successors increment the maximum parent sequence and name the complete maximal
valid parent frontier as sorted unique
`{inventory_sequence,record_digest}` rows. Ordinary succession has one parent
and the accepted predecessor checkpoint; emergency succession names every
competing maximum and the last-common checkpoint. A record activates only at
its exact target generation/sequence and basis, remains effective through
descendants, and is replaced only by a correctly targeted successor.

Records live at
`credential-sync/repository-retention-inventories/<inventory-sequence>-<record-digest>.json`
under the closed
`docs/spec/schemas/comms/repository-retention-inventory-v1.schema.json`.
Each nonempty `repository_refs` row contains exactly:

```text
repository_ref_id, repository_class, repository_rid, ref_name,
object_format, retired, scan_head
```

Class is `config`, `private`, or `public`; scan head is a matching typed Git
object. The ID is domain-separated SHA-256 over exact JCS
`{repository_class,repository_rid,ref_name,object_format}` under
`heterodyne-repository-retention-ref-id-v1`. Rows sort by class/RID/ref UTF-8,
object format, then decoded ID. Ordinary single-parent successors preserve
every semantic row; active scan heads remain equal or advance to descendants,
and retirement occurs only at an equal-or-descendant final head and is
ordinarily absorbing. A new ref is fully scanned before governed use. The
config scan head predates the commit first containing its inventory record.

For candidate checkpoint `C`, `EffectiveRefs(C)` is the complete set of every
`repository_refs` row variant in the activated maximal inventory frontier after
these successor rules; conflicting variants remain distinct and reject
ordinary acceptance. Rows present only in signed ancestor records are
authenticated audit history, not effective registrations.

Config-key acceptance has one controlled deregistration. In ordinary
succession, its successor omits and thereby deregisters exactly the old active
`config` row only when the same transition adds the one fully scanned active
`refs/heads/enc/<new-config-key-id>` row, closure basis `B` proves the complete
decrypted predecessor logical tree was re-encrypted under that new key with no
surviving old-config-key dependency, and the signed multi-ref compare-and-swap
atomically accepts the new ref and deletes the exact old signed ref. This is
not retirement. The predecessor row and accepting transition/CAS remain
required ancestor evidence. Receipts for the accepting candidate still
authenticate and scan the old ref as the exact source/closure basis and verify
the deletion preconditions, while its result `EffectiveRefs(C)` and `K(C)`
exclude that ref. Descendant receipts and archives validate the ancestor and
accepting transition/CAS evidence without fetching or scanning the deleted
ref. No other ordinary transition may deregister a row.

An emergency successor contains the union of semantic rows from
`EffectiveRefs` of every maximal parent plus valid new rows. Branch absence is
never deletion: a branch-only or unique shared row persists, advances
ordinarily, or explicitly retires at an equal-or-descendant cut. A prior valid
config deregistration suppresses a row only when it is absent from every
maximal parent's `EffectiveRefs`.

After first forming that complete union, emergency config-key acceptance may
subtract exactly `V_old`, the complete variant set for the one old active
`config` semantic identity whose ref name is
`refs/heads/enc/<old-config-key-id>` and whose current signed target is the
transition's `source_ref_head`. Every maximal-parent variant of that semantic
identity is in `V_old`. Reset `K(I)`, closure basis `B`, and class-complete
actions must authenticate and scan every variant tree, terminally account every
locator/binding/obligation pair, re-encrypt the complete logical union under
the one fully scanned new active config row, and prove no result dependency on
the old config key. The same reset CAS accepts the new ref and deletes the
exact old signed ref. Accepting-reset receipts scan every `V_old` variant as
source/closure evidence; result and descendant `EffectiveRefs(C)`/`K(C)`
exclude them, while every ancestor record and reset/CAS proof remains audit
evidence. Partial-variant, wrong-identity, wrong-ref, or different-ref
subtraction rejects, and every row outside `V_old` remains in the emergency
union. Only present variants outside this terminal deregistration that disagree
use `H*` convergence.

The replacement keeps the semantic ID and uses a pre-materialized, fully
scanned `H*` whose complete direct-parent set contains every distinct variant
head sorted by decoded OID and nothing else; retirement-only disagreement uses
the shared head as sole parent. Its retired value is the reset's signed result,
and a retired config resolution includes a separate active config row. Every
maximal inventory variant is in `previous_records`.

Reset `K(I)` first derives:

```text
L(S) = all allocated/authenticated marked decrypt-dependency artifact locators
       across every parent exact tree, regardless of parent-local currentness
Bound_I(locator) = every source-profile-embedded tuple plus every tuple in
                   every individually valid signed-binding variant for the
                   locator across all parent K(I) branches, including every
                   conflicting variant
D(S) = { (locator,tuple) |
         locator in L(S) and tuple in Bound_I(locator) }
Current_I(tuple) = true only when every applicable parent agrees it is the
                   same sole current instance and every complete applicable
                   projection exists with no retirement, competition, or
                   different-current state
L(S) = preserved_at_H_star disjoint-union
       reencrypted_or_replaced disjoint-union
       deleted_and_closed
U(S) = { (locator,tuple) in D(S) | not Current_I(tuple) }
ResultPairs(H*) = authenticated fresh-H*-locator pairs supported by actual
                  result profile/ciphertext validation: all embedded tuples,
                  or exactly one independently validated nonconflicting fresh
                  binding where the profile cannot embed a tuple
Current_B(tuple) = ordinary post-reset unique-current predicate replayed from
                   projected result B after all class actions; true only for
                   one complete nonconflicting current instance
```

Missing candidate binding bytes keep reset pending. Missing applicable state
or any disagreement is conservatively noncurrent, so an artifact current on
only one branch still enters `U(S)`. Class-complete actions give every physical
`L(S)` locator one disposition and terminally map every old `D(S)`/`U(S)` pair
to an identical tuple at a fresh result locator, reencrypted/replaced,
binding-candidate-resolved-and-closed, or deleted-and-closed. Current locators
cannot vanish. Legitimate embedded multi-tuples remain multiple result pairs.
A conflicting unembedded candidate becomes a fresh result only when every
candidate is accounted and actual profile/ciphertext validation independently
supports one unique fresh binding; otherwise it is replaced, deleted, or
closed as audit evidence, never selected by arrival or digest order. Active
obligations and any required fresh bindings apply only to noncurrent
`ResultPairs(H*)` under `Current_B`; rejected candidates remain cleanup/audit
evidence. The transition replaces old-head obligations and yields
`G(B) = O(B)`.
Reusing old locators/bindings, omitting candidate bytes, or selecting a
candidate rejects. Only this path may advance/reactivate a retired variant;
ordinary successors, digest selection, non-common descendants,
missing/extra-parent or unscanned merges, branch-only omission, and incomplete
dispositions reject.

Scanning means the recursive tree selected by each cut in `EffectiveRefs(C)`,
not ancestor trees or loose objects. Ciphertext absent from that tree is audit
residue unless an explicit frozen registered ref retains it. All target-roster
nodes authenticate every effective RID/ref, signed ref, authorization, object
format, ancestry, and scan cut; a validly deregistered config ref is checked
through its ancestor record and accepting transition/CAS instead and is not
fetched or scanned. Post-cut old-key content is noncanonical. The current epoch
signs the domain-separated JCS record. Emergency uses the fresh reset epoch and
activates only with the reset checkpoint.

At checkpoint `C`, `K(C)` contains exactly:

```text
{repository_inventory_records,governed_heads,binding_records}
```

`repository_inventory_records` is the complete activated maximal frontier
retained through `C`, including every conflict variant and each record's
ancestor graph. Conflict rejects ordinary acceptance; emergency reset merges
the complete branch frontier with one fresh record.
`governed_heads` is the sorted unique
`{owner,repository_rid,ref_name,repository_head}` set derived from
`EffectiveRefs(C)`. For each active or retired cut, validators scan every
noncurrent marked dependency under its one registry-selected authenticated
source profile and emit exactly one row for each distinct allocated `owner`
produced by those locator expansions. One mixed-owner cut therefore emits
multiple rows; a cut with no noncurrent dependency emits none. Rows sort by
owner, RID, and full ref-name UTF-8, then object-format ASCII and decoded OID.
A fallback binding's retained-ciphertext `owner` must equal its selected source
profile owner; missing, extra, or mismatched head-owner projections reject.
Current-key posts do not change the set. Retained-set changes advance the
inventory cut and project snapshots in the same transition.
`binding_records` is the complete sorted unique deterministic binding frontier
for dependencies found under the closed allocated source-profile table,
including conflicts; a binding with no enumerated dependency is extra.

The checkpoint continues to hash the enlarged closed `K(C)` under
`heterodyne-governed-decrypt-key-binding-set-v1`. Inventory-frontier or
scan-cut drift with an unchanged digest rejects. Every receipt independently
fetches and scans all exact cuts and recomputes inventory, governed-head,
binding, profile-expansion, and conflict completeness.

Artifact `A`, optional later binding record `K`, repository inventory `R`,
obligation `O`, transition `T`, checkpoint `C`, and receipts are acyclic:

```text
accepted predecessor -> artifact A -> optional binding K ->
repository inventory R -> obligation O -> transition T -> checkpoint C ->
receipts
```

These arrows are logical record dependency and signing order, not canonical
Git tree-entry order and, for a config-key transition, not necessarily
distinct commits. Closure basis `B = result_basis.config_head` remains the
parentless new-key root and the new active config row's pre-inventory
`scan_head`. Every artifact and scan head preexists `R`. A required `K` is
signed after its locator exists and before `R`; it is either already reachable
at an independently authenticated pre-inventory head or, when its locator
commits `B` and embedding it in `B` would self-reference, first carried in
direct-child commit `T`. That commit may atomically carry finalized `K`, `R`,
`O`, every `O`-dependent source/assignment/retirement and transition-action
record, reset where applicable, and the transition, but their bytes and
signatures are produced in dependency order and none names `T`'s commit OID.
Result and target digests project those records. New transition-bound
`K`/`R`/`O` and dependent proof records are not placed in `B`; copied
predecessor audit records remain there.

`R` names only its basis and parent frontier. An unmarked ciphertext,
missing/late/conflicting binding,
unregistered ref, scan-cut or tuple mismatch, or obligation as sole tuple
source rejects. Closure, receipt, reset, archive, candidate audit, and CAS
replay preserve every artifact, inventory record/frontier/cut, binding, and
obligation.

Archive credential high-water and every archive/restore-basis carrier of
`governed_decrypt_key_bindings_sha256` inherit the enlarged `K(C)` without a
new digest. Standalone archives preserve every frontier/ancestor record,
registered repository bundle and exact scan cut, Radicle/signed-ref proof,
governed snapshot, profile marker, binding, locator, obligation, and provenance
needed to recompute it. Network-assisted mode cannot externalize that evidence.
Manifest, generation/finality, offline intent/activation, transfer grant,
restore comparison, and rollover reject an unchanged digest when inventory
state drifts.

One encrypted ADR-038 large-object pointer may create two independent
dependencies. Its authenticated profile emits a `git-blob` locator for the
encrypted pointer/wrapped-DEK blob bound to the config/Tier-3 audience tuple
and a distinct `large-object` locator for stored ciphertext bound to the object
DEK tuple. Both complete tuples are embedded by the pointer profile or resolved
through their distinct locator-derived bindings. If both keys are historical,
`G(C)` and the obligation set contain both rows; collapsing or omitting either
rejects.

Retained ciphertext that still requires a retired secret is canonical
credential state. The closed
`heterodyne.historical-decrypt-obligation.v1` record contains exactly:

```text
type, persona, obligation_id, lineage_sequence, previous_record, action,
secret_class, secret_id, instance_commitment, retained_ciphertexts,
retired_provenance_lineages, transition_id, issued_at, authority, signature
```

`obligation_id` is 16 fresh random bytes encoded as 32 lowercase hexadecimal
characters. A root has sequence zero, null predecessor, and
`action:"retain"`. Each successor increments by one and names the complete
preceding record digest.
`retain` requires a nonempty ciphertext array. `close` requires an empty
array, repeats the complete predecessor identity, and is absorbing; later
retention uses a fresh obligation ID. Every successor's retired-provenance
set is a superset of its predecessor and adds exactly the assignment retirements made
effective by that transition; no prior row disappears or changes. Records are
stored at:

```text
credential-sync/historical-decrypt-obligations/
  <obligation-id>/<lineage-sequence>-<record-digest>.json
```

`lineage_sequence` and `issued_at` are JSON-safe nonnegative integers,
successor `issued_at` never decreases, and `transition_id` is 32 lowercase
hexadecimal characters. A root transition retires the old assignments while
preserving governed ciphertext; a retain update changes the exact retained
artifact set without authorizing new encryption under the old key; and a
close transition reencrypts or removes every remaining governed dependency.
`authority` is the closed `{signer_type,signer,kel_head}` selected by that
transition's class-complete authority rule. The selected epoch or cold root
BIP-340-signs SHA-256 of
`UTF8("heterodyne-historical-decrypt-obligation-v1")`, a zero byte, and the
UTF-8 JCS record with `signature` omitted; the signature is encoded as 128
lowercase hexadecimal characters.

Each strictly sorted closed `retained_ciphertexts` row contains exactly:

```text
storage_class, owner, repository_rid, repository_head, ref_name, path,
git_blob_oid, object_id, ciphertext_sha256, ciphertext_length
```

`repository_head` and `git_blob_oid` are each the closed typed-Git object
`{object_format:"sha1"|"sha256",oid}` and use the same format. A SHA-1 OID
has exactly 40 lowercase hexadecimal characters and a SHA-256 OID exactly 64;
mixed formats, bare strings, or wrong lengths reject. Only the actual SHA-256
members `object_id` when non-null and `ciphertext_sha256` are unconditionally
64 lowercase hexadecimal characters.
The exact row comparator compares `storage_class`, `owner`, and
`repository_rid` by UTF-8 bytes; `repository_head.object_format` by ASCII and
its decoded `oid`; `ref_name` and `path` by UTF-8; then
`git_blob_oid.object_format` and decoded `oid`; null `object_id` before a
non-null decoded digest; decoded `ciphertext_sha256`; and finally numeric
`ciphertext_length`. Equality under the complete comparator is a duplicate and
rejects.

Each strictly sorted closed `retired_provenance_lineages` row contains
exactly:

```text
holder_nid, assignment_id, source_record_digest,
assignment_record_digest, retirement_record_digest
```

Every ciphertext/pointer and its authenticated secret-tuple binding must exist
before the obligation. A config-repository artifact head is a strict ancestor
of the commit first storing the obligation; an independently governed
repository/object head is co-bound by the later checkpoint. No locator may
name the config, transition, or checkpoint head containing the obligation,
and no artifact may depend on the obligation or its future checkpoint. This
enforces the acyclic order artifact, obligation, transition/checkpoint.

At candidate checkpoint `C`, a verifier derives `G(C)` from every canonical
retained ciphertext/pointer and its preexisting authenticated profile or
canonical key-binding record. That independent evidence, never the obligation

Genesis and every routine config-key transition use a closed, receipt-only
RFC 9180 HPKE recipient array with exactly one entry for every candidate
roster NID. Emergency reset uses a distinct cold-root-bound recipient array.
The arrays may travel over authenticated DR, local IPC, or offline media and
are the sole pre-receipt config-key delivery paths. Possession permits only
candidate inspection and receipt; publishing, minting, serving, and other
operational authority remain held until atomic acceptance. Each one-use
X25519 key is erased only after the candidate key and signed staging head are
durably retained and the receipt succeeds.

An added NID with no pre-existing credential-sync authorization receives no
credential-sync grant, protected keys-repository transfer, or successor
credential while its roster addition is pending; the config bootstrap is its
sole secret-bearing admission path. Only after roster acceptance may a
separate authorization mutation and fully receipted checkpoint grant
credential sync and stage protected-key transfer. Promotion of an already
authorized durable holder causes no new transfer, and its prior exposures must
already be in the conservative inventory.

Node removal and candidate delivery are modeled as exposure, not as claimed
local erasure. Generic source companions and mergeable assignment-ID lineages
form the canonical append-only inventory. Every valid assignment is counted
until an accepted transition makes its exact retirement effective; staged
successors count immediately, while pending retirements remove nothing.
Abandoned config-key candidates remain as inert signed staging refs, their
keys are burned for operational reuse but retained under protection for
audit/recovery. An abandoned same-key candidate remains on the active audit
chain and creates no nonactive staging ref or candidate key. In either form,
its assignments remain in later inventories until canonically retired or,
for the exact safe current-epoch tuple only, narrowly adopted.

The conservative set includes every unretired assignment lineage reachable
from the inventory basis, including staged, operationally non-authoritative,
and competing variants. Every closed exposure contains exactly
`secret_class`, `secret_id`, `secret_commitment`, `holder_nids`,
`assignment_record_digests`, and `pre_unseal_intent_items`.
The intent array contains exact sorted unique closed
`{intent_record_digest,preimage_id}` rows. Holder and assignment arrays are
independently complete actual-assignment projections and may both be empty
only when no actual assignment origin exists. The intent array is
independently exact and may be empty only with no intent origin; every
exposure has at least one origin, and all co-keyed origins appear.

Every mode processes the sorted union of its mandatory tuples and the complete
cleanup set: each tuple held by a target-excluded NID, containing an assignment
staged by an unaccepted transition, containing a competing assign variant, or
containing an unreconciled intent origin. Once a tuple qualifies, all of its
actual assignment and intent origins are included. Actual assignments retire
one-to-one; intents never receive retirement records. Routine rotation therefore has
the current config-audience tuple as a mandatory minimum, and routine addition
has the current config-audience and OIDC pairwise tuples as mandatory minima;
neither mode uses an exact-only exposure array. Routine key rotation may also
carry an explicitly proven maintenance set for retained-holder expiry,
withdrawal, replacement, or ordinary key retirement. That is the only
caller-selected addition; it cannot omit a mandatory or cleanup tuple.

`oauth-pairwise` and `epoch` are singleton capability classes and close as
classes, not as unrelated exposure tuples. If any pairwise tuple enters the
mandatory, cleanup, or maintenance set, the transition also includes the
predecessor's exact current operational tuple, retires every old,
failed-candidate, and competing pairwise tuple, and creates exactly one fresh
successor identity and commitment. The transition target and successor
checkpoint name that same commitment.

Epoch handling first resolves the exact current canonical Core KEL key/head and
its complete assignment tuple. That tuple may survive an abandoned config
candidate only when every assignment binds that exact KEL event, has no
competing variant, and names only holders allowed by the target recovery
policy. A successor may then adopt that already-current tuple while retiring
every noncurrent epoch tuple. If the current tuple has an excluded holder,
competition, or another unsafe assignment, the cold root performs one further
canonical rotation to one fresh epoch tuple. Every epoch action in one
transition converges on that single successor; selecting an older tuple or
creating two current epoch singletons rejects.

Each closed transition-action record contains exactly:

```text
type, persona, transition_id, action_kind, secret_class, secret_id,
old_commitment, disposition, successor_id, successor_commitment,
excluded_nids, authorized_nids, source_assignment_digests,
pre_unseal_intent_items,
retirement_record_digests, successor_assignment_digests,
historical_decrypt_nids, historical_assignment_digests,
artifact_refs, created_at, authority, signature
```

`historical_decrypt_nids` is a sorted unique canonical-NID array and
`historical_assignment_digests` is sorted uniquely by decoded digest. Both are
empty unless projected `G(B) = O(B)` has an active retain for the exact old
tuple; because the complete old assignment set retires, both are nonempty when
that tuple remains required. The NID set is exactly the target-roster
recovery/decrypt-only holders authorized by class policy and may overlap, but
is independent from, `authorized_nids`.

The assignment set is a complete one-to-one projection of those holders. Each
new assign has a fresh assignment ID, the action's exact transition ID, and
the same old secret ID/commitment. It names a newly staged or already-current
nonretired source companion whose `artifact_refs` bind the complete
projected-active retain-obligation head set for the tuple and every applicable
key binding/governing artifact. A stale source without those refs cannot be
reused. The current epoch, or fresh canonical recovery epoch in emergency
mode, signs the ordinary source/assignment records.

All old operational and prior historical assignments retire atomically and
populate every projected-active obligation record's retired provenance. The new historical
assignments enter the result exposure digest atomically, alongside any
distinct fresh-current successor assignments, but authorize only decrypting
the exact `G(B)` rows covered by their obligation/binding proofs. They cannot
authorize new encryption, signing, delegation, minting, serving, or other
authority. A transition that closes the final matching obligation retires the
complete historical set and carries both arrays empty. This historical overlay
does not add another class action/disposition to the matrix below.

Each exposure has exactly one class-selected action and disposition. Cold-root
exposure requires terminal persona migration; epoch exposure requires KEL
rotation; device and agent keys require delegation revocation; protected
records and recovery wraps require wrapper replacement; config, Tier 3, and
claim-ledger audiences require audience-key rotation; object DEKs require
object-key replacement; Double Ratchet state requires termination; repository
access requires ACL revocation; OAuth, bearer, SSH, onion, and TLS
capabilities require their exact rotation, revocation/reissuance, retirement,
or endpoint replacement action. Every action names the exposure's complete
unretired conservative assignment set from `EffectiveInventoryItems`,
including staged, non-authoritative, competing, retained-holder,
target-excluded-holder, and unreconciled offline provisional variants; when
both offline inventories are empty this equals ordinary predecessor exposure
replay. Its `pre_unseal_intent_items` JCS-equals the exposure's complete
intent-origin array. It names exactly one retirement per actual assignment
digest and no retirement for an intent origin; both assignment arrays are
empty exactly for an intent-only exposure, which still requires the same
class-complete action, successor/termination effect, checkpoint, and rollover.
Its
`authorized_nids` is the exact
class-specific post-transition holder set; `excluded_nids` is exactly the old
holder set minus that set. The excluded set and the intersection of old
holders with `authorized_nids` form the disjoint complete old-holder
partition; `authorized_nids` may also contain new successor holders.
Where applicable, the action stages exactly the successor assignments for the
authorized post-transition holders.
`recovery-wrap` never uses `historical-decrypt`: a surviving protected item is
rewrapped under the successor, while the old wrapper and retired
archive/protected-record generation cease to be live. Archive recipient slots
remain independently recoverable and cannot create a governed dependency
outside the closed Git-blob/large-object locator grammar.
Its proof references may name only noncyclic artifacts finalized before the
action is signed. Existing proofs may be available by closure commit `B`; new
`K`/`R`/`O` records and any `O`-dependent source, assignment, retirement, and
action records may first appear together in carrier `T` only under the logical
dependency/signing order above. They cannot name the enclosing transition,
candidate reset, checkpoint, bootstrap array, receipt, `T`'s commit OID, or
any digest that depends on the action. Authority stays held until every
exposure has the one effective outcome permitted by this matrix. A
`persona-migration-required` outcome is audit-only, makes no retirement
effective under the old persona, and can never accept a transition or
checkpoint.

Transition signing authority is derived from the complete mandatory, cleanup,
and maintenance action set, not merely from the named transition mode.
Emergency reset and any transition that closes `epoch`, `core-protected`, or
`recovery-wrap` exposure, or otherwise changes recovery authority, use the
cold root; every other routine transition uses the current epoch. Every
action, retirement, Double Ratchet termination, and the transition itself
uses that same selected authority. An epoch action additionally binds one
exact canonical cold-root-authorized KEL rotation: its successor, target
event ID, target epoch key/head, and accepted KEL result must all agree. A
cold-root exposure remains a persona-migration condition and cannot be made
acceptable by choosing cold-root transition authority.

A Double Ratchet termination repeats that exact complete assignment set and
partitions its holders into target-excluded `removed_holder_nids` and
`retained_holder_nids` equal to old holders intersected with the authorized
set. Its NID-revocation set contains exactly
those removed holders whose NID or delegated delivery-key authority remains
current and whose class action requires revocation; a never-admitted proposed
NID or unrelated authority does not create a global revocation requirement.

Config-key changes use a parentless new encrypted branch. Source basis `A` is
an authenticated logical/inventory basis, not a Git parent of closure commit
`B`. `B` contains no old-key ciphertext ancestry and copies the complete
decrypted predecessor logical tree byte for byte, except only the paths the
transition explicitly replaces or retires. It preserves the complete accepted
checkpoint/receipt/removal-observation/candidate-abandonment/
staging-ref-cleanup/reset/bootstrap/source/assignment/retirement/transition/
action/DR-termination/repository-retention-inventory/
governed-decrypt-key-binding/historical-obligation/
offline-recovery-pre-unseal-intent/offline-recovery-activation audit
namespace, every intent preimage and intent-to-activation link, every
preexisting provisional source/assignment and assignment-only absorbing
cleanup retirement, and every recovered or failed-staging record needed for
conservative replay. Its child `T` carries any new binding `K`, the targeted
inventory successor `R`, transition-bound obligation `O`, `O`-dependent
source/assignment/retirement records, every transition-action record, the
signed transition, and the emergency reset where applicable, all under the
logical dependency and signing order above. Child `C` adds the checkpoint and
bootstrap array;
checkpoint-receipt and, for routine removal, removed-NID observation commits
descend from `C`.

Every commit and tree reachable from a signed encrypted ref first passes the
closed `comms.config-repository-git-structure.v1` profile. Ordinary commits
have exactly one tree, zero or one state-machine-permitted parent, fixed
protocol author/committer identity with timestamp `0 +0000`, and the exact
`heterodyne-config-v1\n` message; optional headers, continuation headers, and
merges are forbidden.

The sole second branch is a config-class emergency `H*` commit with tree first,
one or more unique parent headers exactly equal to all distinct variant heads
in decoded-OID order, the same fixed author/committer lines, and exact message
`heterodyne-config-retention-resolution-v1\n`. It uses the ordinary canonical
tree/path rules and is valid only when named by the cold-root emergency
repository-inventory resolution whose maximal parent frontier, direct-parent
set, signed result, total `U(S)`, `K(I)`, class actions, fresh bindings and
obligations, exposure cleanup, reset, checkpoint, and receipts verify. An
unbound merge or extra/missing/wrong-order parent or wrong message rejects.
Ordinary config commits remain zero/one-parent. Trees contain only mode
`100644` blobs and mode `40000` subtrees in canonical Git byte order.

Every pathname is either one normative family template whose variable
components are schema-classified public protocol identifiers, or:

```text
config-data/<path-token>.bin
path-token = lowercase_hex(HMAC-SHA256(
  HKDF-SHA256(
    IKM=config_audience_key,
    salt=32 zero bytes,
    info=UTF8("heterodyne-config-path-index-key-v1"),
    L=32
  ),
  UTF8("heterodyne-config-logical-path-v1") || 0x00 ||
  UTF8(normalized_logical_path)
))
```

The logical path is strict UTF-8 NFC and remains only inside the encrypted
blob. A user label, filename, hostname, or other free text never appears in a
Git pathname. Commit metadata and paths are therefore canonical nonsecret
structure; arbitrary configuration values and semantic names remain
candidate-key ciphertext. A noncanonical commit, tree, public component,
HMAC token, or secret-bearing pathname rejects before candidate delivery or
signed-ref publication.

Before any receipt-only delivery, the new signed encrypted ref is durably
published at `C` alongside the old ref. Routine transitions require every
current roster node to verify the exact candidate and signed-ref map before an
added NID receives the key; retained nodes keep the candidate key and head
under protection and receipt it before any other successor secret is
delivered. Removed nodes verify the encrypted publication and issue their
noncyclic observations without receiving the key. Emergency recovery first
persists the reset, transition, candidate, bootstrap, and a cold-root- or
active-recovery-slot-encrypted candidate key in an independent
portable-recovery location.

Except for genesis, every partial checkpoint receipt or removal observation
becomes durable only by a signed compare-and-swap append to the exact current
candidate tip. The direct child preserves every prior byte and adds a
nonempty set of previously absent, byte-identical records at their canonical
paths; deletion, replacement, an unrelated write, or a merge rejects. A
config-key-candidate append also compares the old active ref with the
transition's exact source-ref head. A same-key append compares the one
active/candidate ref and requires that no canonical abandonment is reachable.
Each receipt and observation is fully validated before append. Distinct valid
receipts from one roster NID remain audit evidence but count once; exactly one
observation is permitted per removed NID. A losing concurrent appender retries
the same bytes against the new tip. Orphan and side-branch records never count,
and every successful append recomputes the complete partial-acceptance record
set. No append may follow canonical acceptance or abandonment.

Genesis exposes no signed partial state: its receipt chain is exchanged
privately and the branch is published by one create-only compare-and-swap at
the complete receipt-bearing head.

Config-key acceptance is one signed multi-ref compare-and-swap. It compares
the exact current partial candidate tip, the complete noncandidate signed-ref
map, and the old active tip against the transition; it advances the candidate
to the complete receipt/observation-bearing head when needed and deletes the
old ref atomically while activating the successor inventory that deregisters
exactly that ordinary old config row or the emergency transition's complete
`V_old` under the rules above. A same-key candidate instead accepts by the
append compare-and-swap that first produces the complete head; no no-op
acceptance transition exists. Any concurrent old-ref or staging-ref change invalidates
a config-key candidate and requires rebuilding from the new basis. Failure of
that config-key acceptance leaves the old checkpoint authoritative and the
new ref durably inert.

The transition persists the exact sorted `signed_ref_map` array of closed
`{ref,head}` entries as well as its domain-separated digest; the absent
candidate ref is not an entry. Acceptance and cold replay verify that exact
preimage, not merely a locally reconstructed digest. Every other staging
entry names its exact current append-only partial tip, not an earlier `C`.
The old active ref is the sole signed encrypted ref whose graph intersects the
old generation; every staging ref begins at a parentless, graph-disjoint root.
An equal head, shared ancestor, or omitted old-generation alias rejects rather
than being left behind by the acceptance CAS.

The complete acceptance
head must descend from `C` and make the candidate checkpoint, at least one
valid receipt from every target-roster NID, and, for routine removal, exactly
one observation from every removed NID and none from any other NID reachable
together. Distinct valid duplicate receipts remain reachable but count once.
Orphaned, side-branch, missing, invalid, out-of-roster, or extra observation
records reject.

An otherwise valid successor cannot remain pending forever. While its
predecessor is still authoritative, the current epoch may publish one
absorbing, epoch-signed candidate-abandonment record containing exactly:

```text
type, persona, predecessor_checkpoint, candidate_checkpoint_digest,
candidate_transition_id, candidate_transition_digest,
candidate_ref, candidate_head, abandonment_ref, abandonment_basis_head,
partial_acceptance_record_set_sha256, candidate_exposure_records,
candidate_governed_decrypt_key_bindings_sha256,
candidate_historical_decrypt_obligations_sha256,
abandoned_at, epoch_pubkey, kel_head, epoch_signature
```

It names the exact
candidate checkpoint and transition, candidate and authoritative refs/heads,
and a domain-separated digest of every valid partial receipt and observation
reachable from the compared candidate tip. Its signed compare-and-swap freezes
that exact partial tip and recomputes the set before advancing the
authoritative ref; an invalid, extra, or omitted record rejects.

The abandonment also binds `candidate_exposure_records`, a complete
verifier-derived, strictly ordered unique array of closed
`{record_type,record_digest}` objects for every node-secret source and
`action:"assign"` exposure record newly reachable at the candidate
checkpoint's exact `config_head` relative to the accepted predecessor's
operational config state. `record_type` is exactly `secret-source` or
`secret-assignment`, in that order, followed by decoded digest bytes.
Inherited byte-identical records, later writes, retirements, and other record
classes are excluded; each newly reachable assignment must resolve its source
in the same delta or predecessor. The validator independently derives and
recomputes this array at abandonment CAS acceptance, so an ordinary
null-transition candidate cannot hide an exposure addition merely because it
never created a staging ref.

The same abandonment record separately carries
`candidate_governed_decrypt_key_bindings_sha256`, equal to the candidate
checkpoint field and independently recomputed as complete `K(C)` from its
exact `config_head`. Append and abandonment replay reject an omitted/extra
retention snapshot or binding, conflict variant, marker, or locator mutation.
It also carries
`candidate_historical_decrypt_obligations_sha256`, equal to the candidate
checkpoint field and independently recomputed from its exact `config_head`.
Append and abandonment replay reject an omitted retain/close record, hidden
competing branch, changed provenance, or governed-locator mutation. Every
newly reachable obligation record remains preserved as inert audit evidence
even though abandonment prevents its candidate projection from becoming
authoritative.

Candidate append, acceptance, abandonment, and emergency reset are one ordered
state machine. If an append wins first, an abandonment or reset over the stale
tip must be rebuilt. If abandonment wins first, later append and candidate
acceptance fail. If acceptance wins first, abandonment and reset from its old
basis fail. A reset inventories and compares every staging ref at its exact
current partial tip, so an earlier append makes that reset stale and an
accepted reset prevents any later append. A cold-root reset and epoch
abandonment likewise compare the authoritative old ref/inventory and cannot
both win. No timestamp or local flag terminalizes a candidate.

A later successor begins from the post-abandonment authoritative basis. For a
config-key abandonment it inventories the inert candidate ref and every
staged exposure, retires or narrowly adopts them under the epoch singleton
rule, and later uses authenticated staging-ref cleanup.

For a same-key abandonment, the candidate and authoritative ref are the same
active ref, so there is no nonactive staging ref or candidate key to clean.
The next transition instead treats every `secret-assignment` in
`candidate_exposure_records` as mandatory cleanup. Only the exact current
canonical epoch tuple may be narrowly adopted; every other assignment is
retired, and a still-desired non-epoch capability is recreated with a fresh
successor source and assignment. The source records and absorbing retirements
remain on the active audit chain. Staging-ref cleanup is neither required nor
permitted for this same-key case.

If ordinary epoch authority or a unique candidate is unavailable, the
cold-root reset is the only alternate escape.

Retiring staged assignments does not delete their encrypted ref. A separate
epoch-signed staging-ref-cleanup record may delete one exact inert ref only
after an accepted abandonment or reset has terminalized that candidate and a
later accepted transition has retired every attributable exposure, except an
exact safely adopted current-epoch subset. The terminalization record and the
signed-ref compare-and-swap that made it canonical are verified explicitly;
timeout, a local flag, a failed validation, or a merely newer checkpoint is
not terminalization.

Cleanup preserves the complete authenticated raw Git object closure from the
candidate's parentless basis through its frozen staging tip. Its signed opaque
manifest commits each commit, tree, and blob object ID, raw-body SHA-256,
reachable nonsecret paths, disposition, and audit destination. Every
non-inherited commit, mixed tree, and candidate-key-encrypted blob is copied
without decryption to:

```text
credential-sync/staging-ref-audit/<staging-config-key-id>/<staging-head-token>/
  objects/<object-type>/<object-id>.bin
```

Arbitrary configuration, pairwise secrets, bootstrap ciphertext/plaintext,
bearer credentials, and other secret-bearing candidate material are never
decrypted and republished beneath the active key, and neither are their bare
plaintext hashes. The sole decrypted-copy exception is the closed set of
schema- and signature-valid, nonsecret credential-control records required for
cold replay. An already accepted cleanup namespace may be represented by its
prior signed cleanup digest and whole-subtree raw commitments; a prospective,
mutated, incomplete, or unaccepted audit-prefixed namespace remains ordinary
opaque candidate material rather than inheriting audit status.

The cleanup binds the complete safe-record set, opaque-object set, inherited
cleanup digests, assignment set, adopted epoch subset, and one-to-one
retirement set. One atomic multi-ref compare-and-swap advances the active ref
and deletes only the still-identical inert staging ref. Until it succeeds, the
ref remains in the signed-ref map, its protected key remains decryptable, and
every later transition inventories it. A cleanup/transition race forces the
loser to rebuild; key erasure follows successful cleanup and never precedes
it. This cleanup profile applies only to a distinct inert config-key staging
ref; it never fabricates a cleanup target for a same-key abandonment.

Permanent node loss or an active offline intent- or activation-ID collision additionally
requires a cold-root-signed emergency reset that binds the exact old/new
rosters, unavailable nodes, last common accepted checkpoint, new generation,
fresh config and pairwise keys, fresh compromise-cutoff epoch/KEL state,
exposure transition, collision evidence, and recipient array.
The reset record contains exactly:

```text
type, reset_id, persona, prior_generation, new_generation,
last_common_checkpoint, old_roster, new_roster, unavailable_nodes,
prior_config_key_id, new_config_key_id, new_config_key_sha256,
prior_pairwise_secret_sha256, new_pairwise_secret_sha256,
lost_audit_set_digest, same_key_candidate_audit,
offline_recovery_pre_unseal_intents,
offline_recovery_pre_unseal_intent_collisions,
offline_recovery_activations, offline_recovery_activation_collisions,
exposure_set_sha256,
governed_decrypt_key_bindings_sha256,
historical_decrypt_obligations_sha256, secret_transition_digest,
epoch_rotation_event_id, new_epoch_pubkey, new_kel_head, compromise_since,
bootstrap_recipients_digest, created_at, reason, cold_root_signature
```

The reset's four offline arrays and same-key audit JCS-equal the corresponding
transition inventory members. Both intent/activation evidence arrays are exact
unreconciled projections; both collision arrays are complete active
projections and may include already-reconciled evidence-only variants. Its
exposure, governed-binding, and obligation digests
equal the transition target, `result_basis`, and sequence-zero checkpoint.
Reset construction inventories every retention snapshot, binding frontier,
obligation branch, governed locator, current and retired provenance lineage,
and every intent or activation named by any offline array. A newly discovered
branch, locator mutation, intent, or activation variant makes the reset basis
stale and holds authority until reconstruction.

The reset reason is exactly
`credential_ledger_reset_node_loss` or
`credential_ledger_reset_offline_activation_id_collision`.
For node loss, `unavailable_nodes` is nonempty and
`transition.removed_nids == unavailable_nodes == old_roster - new_roster`;
every other old-roster NID remains. For collision-only reset,
`unavailable_nodes == transition.removed_nids == []`,
at least one of `offline_recovery_pre_unseal_intent_collisions` or
`offline_recovery_activation_collisions` is nonempty, and `old_roster` is a
subset of `new_roster`. In both cases
`transition.added_nids == new_roster - old_roster`; additions may be empty and
each nonempty addition independently satisfies the existing delegation,
recipient, bootstrap, and receipt rules. If any old-roster node is unavailable,
node loss takes precedence even when collision evidence is present. No
arrival-order collision winner is implied by an addition.

Both reasons start a fresh generation at sequence zero, rotate the current
epoch, config-audience key/ID, and OAuth pairwise secret, and require all
target-roster receipts. `compromise_since` remains a required JSON-safe
nonnegative integer, is no later than the KEL rotation's `created_at`, and
equals that event's sole canonical tag. For collision-only reset, let
`CurrentEpochCollisionExposures` contain unreconciled intent-collision
variants whose exact templates plan release of the last-common checkpoint's
current epoch, plus unreconciled activation-collision variants whose completed
records resolve to that tuple. Every activation resolves its exact intent, and
the cutoff uses the linked intent `created_at`, never the later activation
time. If the set is nonempty, `compromise_since` is no later than both its
earliest intent time and the first collision-detection boundary; otherwise it
remains no later than detection.
Reconciled historical variants remain evidence-only and do not move this new
cutoff backwards. A healthy prior roster does not downgrade the
compromise-declaring rotation. New epoch/config keys,
successor assignments, deliveries, and roles exclude every target-excluded
collision NID. A target-included claimant completes the ordinary delivery and
role gates; a target-excluded claimant is reconciled only by complete terminal
cleanup.

The reset and its emergency transition inventory also carry byte-identical
`same_key_candidate_audit` values. It is null only when the exact active
source-ref tip contains no unaccepted same-key candidate; otherwise it is the
closed object:

```text
predecessor_checkpoint, candidate_checkpoint_digest,
accepted_basis_head, candidate_head, candidate_exposure_records,
candidate_governed_decrypt_key_bindings_sha256,
candidate_historical_decrypt_obligations_sha256,
opaque_object_manifest, opaque_object_manifest_sha256,
safe_record_copies, safe_record_set_sha256
```

`accepted_basis_head` is the signed-ref head containing the fully receipted
predecessor. `candidate_head` is the exact current `source_ref_head`, descends
from that basis, reaches the unaccepted checkpoint and all durable partial
receipts and security writes, and has no successful acceptance or
abandonment. The verifier independently derives the same
`candidate_exposure_records` delta used by abandonment and the exact candidate
governed-binding and obligation-frontier digests; it cannot inherit the
predecessor values when the candidate projected a retention snapshot, binding,
retain, or close.

The raw and safe manifests reuse the staging-cleanup grammars and digest
domains, but copy into the deterministic
`credential-sync/reset-candidate-audit/<reset-id>/<candidate-checkpoint-digest>/`
namespace. They cover the complete raw Git object closure from
`candidate_head` through and including `accepted_basis_head`, never traversing
a parent before that accepted basis, plus the complete newly reachable
safe-record set, including the candidate checkpoint, every partial receipt,
independently authoritative security-critical write, and allowlisted
source/assignment, offline-recovery-pre-unseal-intent/activation,
repository-retention-inventory, governed-decrypt-key-binding, and
historical-obligation records. Old-active-key ciphertext and canonical commit/tree
structure remain opaque raw objects; arbitrary or secret-bearing plaintext is
never promoted. Closure basis `B` must reach every named copied byte before
the reset or transition is signed.

These copies are non-authoritative audit evidence. They cannot grant or
resurrect authority, but an independently authoritative monotonic revocation,
retirement, or other security reduction found in the bounded suffix is also
preserved byte-identically at its canonical operational path and retains its
ordinary effect. Every assignment in the bound exposure delta is mandatory
cleanup for the emergency transition: only the exact safe current-epoch tuple
may use the narrow adoption rule; every other assignment is retired, and any
desired capability is represented by a fresh reset successor.

The reset acceptance CAS requires
`source_ref_head == same_key_candidate_audit.candidate_head` and verifies that
`B` already reaches the complete bound audit copies. If a same-key receipt
append or security write advances that tip first, the reset and its full
audit must be rebuilt; if reset acceptance wins first, deletion of the old ref
cannot lose the suffix. When the reset inventory uses config deregistration,
that same CAS deletion terminalizes exactly complete `V_old`; any missing
variant accounting or subtraction of another semantic identity rejects.

The last-common authorization set carries forward byte-identically; other
valid recovered authorization records remain in a digest-bound audit-only
namespace. Conflicting non-credential path states preserve every available
present-byte or deletion variant under
`credential-sync/lost-generation-data/<prior-generation>/<path-sha256>/`;

### 13. Require independent conformance evidence

Every current normative vector, including one governed by registry revision
1, 2, or 3, upgrades to the new vector envelope and names an executable
validator/replayer or an explicit evidence class. Its historical
`registry_revision` remains the profile/allocation genesis pin, not an
immutable behavior snapshot; current pre-1.0 behavior is identified by owner
version plus the selected content-addressed owner/dependency artifact set. A
separate allocation-catalog revision and digest resolve symbols that did not
have catalogs in revisions 1–3, and evidence independently pins that catalog.
Historical registry snapshots are not backfilled.

Vector schema `2.0.0` therefore requires `registry_sha256`,
`allocation_catalog_revision`, `allocation_catalog_sha256`,
`registry_allocations`, and `evidence`, plus `validator_operation` exactly
for `executable`, `cryptographic-known-answer`, and `schema-only` evidence;
`documented-nonwire` has no validator operation.
`registry_allocations` lists every protocol symbol directly exercised by the
case and resolves it in the independently pinned revision-4 catalog;
validator IDs are tooling and are not historical protocol allocations.
Produce, consume, replay, round-trip, and isolated validate are separate
contracts and cannot substitute for one another.

`evidence.expected` must JCS-equal the vector's authoritative
`expected_output`. Each executable validator catalogs a closed input and
closed complete-result schema for every exact `(profile,operation)` pair.
Existing decision traces, `expected_*` values, per-case verdicts, and other
oracles move out of `/input`; only genuine candidate-artifact fields may share
a verdict-like name. The harness validates input before invocation and both
expected copies plus the result before JCS equality.

Before inspecting a result, the conformance invocation explicitly selects
`current` with the owner release's top-level artifact pair or `historical`
with one exact append-only superseded pair. The harness never searches for a
manifest containing matching vector bytes or chooses between corpora after
execution; the report records the selected pair and recursively verified
dependency pairs.

The harness gives an executable validator only non-oracle artifact context,
registry/allocation pins, direction, profile, operation, and
contract-validated `/input`. It withholds the vector ID, allocation list,
expected output, evidence, descriptions, network, ambient time/randomness,
and unverified files. A validator has one canonical ID and content-addressed
bundle path. Its exact-JCS bundle contains one fixed WASI Preview 1 command
entrypoint plus only non-oracle support files, all regular and digest-pinned;
canonical schemas remain harness-owned files in the artifact closure and are
neither copied nor preopened in the bundle. Vector, generator,
expected-output, KAT source/case-map, release, registry, review, and ADR
material is categorically unavailable to the module.

Each validator registry entry binds one canonical ID and implementation family,
its exact profile/operation contract projection, input/result schema
path/digests and semantic-or-cryptographic assurance, runner protocol
`heterodyne-vector-validator-stdio-v1`, and content-addressed
bundle/provenance manifests. The bundle root is exactly
`docs/spec/validators/<validator-id>/<bundle-manifest-sha256>/`; the manifest
is exactly `bundle-manifest.json`, its raw digest equals both that directory
component and the validator version, and provenance is exactly
`implementation-provenance.json` in the same root. The exact-JCS bundle
manifest contains one `wasm32-wasi-preview1-command-v1` entrypoint and only
digest- and size-pinned `entrypoint` or `non-oracle-support` files.

Validator provenance inventories the authenticated source repository and
immutable revision, every source/build/lockfile byte, the hermetic build recipe
and environment, the complete compiler/linker/runtime/sysroot/transitive-native
toolchain, per-operation lineage, and every direct or transitive cryptographic
implementation. `operation_lineage` is a complete sorted array with one
closed entry for every executable `(profile_id,operation)` pair:

```text
profile_id, operation, decision_source_files, transcript_source_files
```

The pair set equals the artifact's advertised or generated executable
operation set. Each source array is sorted and unique, has a nonempty union
with the other array, and contains only closed `{path,sha256}` references that
resolve byte-identically in the provenance source inventory.
`decision_source_files` covers every replay, state-transition, comparison,
verdict, and reason path. `transcript_source_files` covers every
canonicalization, serialization, domain-separation, identifier/signature
transcript, and expected-result construction path. Build-dependency tracing
and source review establish completeness; hiding shared logic in a wrapper,
generated file, generic helper, or unlisted transitive library invalidates the
provenance.

Provenance is eligible only after an independent verifier rebuilds the pinned
source in the hermetic environment and reproduces every entrypoint and support
file byte for byte. A source manifest paired with an unreproducible or
different Wasm binary is invalid even when the two objects hash correctly in
isolation.

The generator has a separate fixed
`docs/spec/vectors/generator/implementation-provenance.json` record with
`artifact_kind:"vector-generator"`. An independent release verifier
hermetically rebuilds and runs it without access to prior vector outputs,
validator bundles, reviews, or the expected-output corpus, then requires every
generated path and byte to equal the externally selected candidate artifact
manifest. Generator provenance uses the same complete `operation_lineage`
shape for every executable operation it generates.

For every executable operation, the generator and primary validator have
distinct independently maintained implementation families and source
lineages. Their selected operation-lineage entries share no decision or
transcript implementation source, fork, generated translation, vendored copy,
wrapper around common logic, or common selected-operation helper. A semantic
contract therefore has null corroborator members but still requires two-way
decision/transcript independence between generator and primary validator;
separate repositories or entrypoints alone are insufficient.

For cryptographic assurance, the primary validator, corroborating validator,
and generator have three distinct implementation families, and the same
pairwise decision/transcript prohibition applies across all three. Every
cryptographic primitive exercised by the operation must also come from three
independently maintained implementations: no pair may share a component
repository, revision, source digest, fork, translation, wrapper, vendored
copy, or common primitive code. Sharing the governing standard, closed
schemas, public algorithm constants, runner ABI, or generic build/runtime
infrastructure is allowed only when that code performs none of the selected
operation's decisions, canonicalization, transcript construction, or expected
derivation. The independently generated expected result and both validator
results must agree after all provenance checks pass.

Before validation or execution, the harness opens every listed bundle file by
a race-safe descriptor-relative, no-follow walk, verifies identity, regular
file metadata, size, and digest from the open handle, and reads it once into an
immutable byte snapshot. Module parsing and virtual `/bundle` reads use only
that snapshot; no host path is reopened, restated, or reread. The same
stable-handle snapshot rule covers the selected vector, registry catalogs,
release, artifact, bundle, and provenance manifests, schemas and local
metaschema, KAT source/map, evidence contracts, and every dependency-artifact
file affecting the run. Digest validation, parsing, request construction,
expected comparison, and reporting all consume those exact snapshots.

Executable evidence uses the frozen
`heterodyne-wasm-core-deterministic-v1` profile: one 32-bit unshared linear
memory, integer numeric/control/call/memory operations, and one MVP `funcref`
table with declared initial and maximum no greater than 65,536. Memory and
table maxima are pre-reserved; `memory.grow` succeeds only through its declared
maximum and `table.grow` is forbidden. Floating-point types or instructions,
SIMD, threads/atomics, shared or multiple memory, memory64, extended references
or GC, exceptions, tail calls, the component model, and every undeclared Wasm
proposal reject before execution.
The only table operations are `table.get`, `table.set`, `table.size`,
`table.init`, `elem.drop`, `table.copy`, and `table.fill`; deterministic
bulk-memory operations are permitted under the same bounded profile.

The only Preview 1 imports are:

```text
fd_read, fd_write, fd_close, fd_seek, fd_tell,
fd_fdstat_get, fd_filestat_get,
path_open, path_filestat_get,
fd_prestat_get, fd_prestat_dir_name, proc_exit
```

Descriptor 0 is the finite nonseekable standard-input stream; 1 and 2 are
finite nonseekable output and diagnostic sinks; 3 is the sole preopen with
guest name `/bundle`; and opened snapshotted files occupy 4 through 65,535,
using deterministic lowest-free allocation and reuse. Only exact listed
canonical relative paths may be opened from descriptor 3, read-only, with
zero flags and exactly read/seek/tell/stat rights. Descriptor rights and
observable seek behavior are fixed:

| FD | Type | Base rights | Inheriting rights | Seek/tell |
|---|---|---|---|---|
| `0` | `character_device` | `FD_READ \| FD_SEEK \| FD_TELL \| FD_FILESTAT_GET` | none | `ERRNO_SPIPE` |
| `1`, `2` | `character_device` | `FD_WRITE \| FD_SEEK \| FD_TELL \| FD_FILESTAT_GET` | none | `ERRNO_SPIPE` |
| `3` | `directory` | `PATH_OPEN \| PATH_FILESTAT_GET \| FD_FILESTAT_GET \| FD_SEEK \| FD_TELL` | `FD_READ \| FD_SEEK \| FD_TELL \| FD_FILESTAT_GET` | `ERRNO_SPIPE` |
| opened file | `regular_file` | `FD_READ \| FD_SEEK \| FD_TELL \| FD_FILESTAT_GET` | none | deterministic success |

All descriptor flags are zero. `path_open` accepts only descriptor 3,
zero directory/open/descriptor flags, base rights exactly
`FD_READ | FD_SEEK | FD_TELL | FD_FILESTAT_GET`, and no inheriting rights.
No attenuation, elevation, path alias, escape, NUL, absolute path, or unlisted
path is accepted. Existence, range, flag, rights, path, and exhaustion errors
follow the frozen precedence in the design record rather than host behavior.
A closed descriptor and wrong-direction I/O return `ERRNO_BADF`; seek/tell on
an open nonseekable descriptor return `ERRNO_SPIPE`.

Vectored I/O validates all ranges and overlap before side effects, transfers
maximally in iovec order, and returns exact counts. Seek/tell, preopen, and
stat results are virtual and host-independent; successful Preview 1 result
structures are exact-size, zero-initialized, and little-endian, with fixed
zero device/inode/time metadata. Clocks, randomness, arguments, environment,
polling, sockets, process spawn, mutation, links/renames, and directory
enumeration are unavailable.

The bundle is capped at 64 MiB, each file/module at 32 MiB, stdin and stdout at
16 MiB each, stderr at 1 MiB, cumulative bundle reads at 128 MiB, and linear
memory at 4,096 pages. Fuel is exactly 1,000,000,000 units, charged once per
core instruction plus `1 + ceil(bytes/64)` for each bulk-memory operation or
WASI transfer; a 120-second wall timeout is only a safety backstop. Any
memory, size, read, output, fuel, or timeout exhaustion is a harness failure,
never a protocol verdict.

The harness supplies exactly one LF-terminated JCS request containing only:

```text
protocol, owner_document, owner_version,
artifact_manifest_path, artifact_set_sha256,
dependency_versions, dependency_artifact_sets,
registry_revision, registry_sha256,
allocation_catalog_revision, allocation_catalog_sha256,
direction, profile, operation, input
```

The current-or-historical owner artifact pair is selected externally before
execution and determines the dependency pairs. `input` is exactly the
contract-validated vector input. The vector ID, expected values, evidence,
descriptions, and `registry_allocations` remain withheld. Success is exactly
one LF-terminated JCS result on stdout and exit status zero; any other stdout
bytes reject.

Direction-to-operation contracts distinguish independent production,
consumption, replay, round trip, and isolated validation. Any produced wire
artifact is validated before return, and an executable reject vector runs the
invalid input to its exact failure.

Executable results, `evidence.expected`, and authoritative
`expected_output` must validate against the same closed result schema and
JCS-equal one another. Cryptographic known-answer evidence instead binds an
independently vendored source, raw digest, exact-JCS case map, source URI,
unique case, and JSON pointers. Its `source_id` must resolve to one
authenticated revision-4 `kat_sources` entry whose immutable authoritative
URI and raw digest equal both evidence and case-map values; floating or
Heterodyne-controlled sources cannot establish independence. Schema-only and
documented-nonwire evidence cannot establish semantic wire conformance. The
content-addressed owner artifact set pins every normative document, schema,
vector, validator bundle, support file, registry context, and exact dependency
artifact set used for that verdict. Replaced `0.x` corpora remain addressable
through the append-only superseded artifact-set list.

Known-answer and schema-only evidence also bind an owner-artifact schema for
the exact closed `{profile,operation,input,result}` contract, including its raw
path and digest; both expected copies must validate through that same contract
before comparison. External KAT evidence is optional and is eligible only
when an authoritative immutable upstream naturally publishes JSON whose
pointer-selected input and expected subtrees exactly match one closed
primitive-validation profile. Composite Heterodyne behavior and non-JSON
BIP-340 CSV, RFC prose, or NIST-style suites require independent executable
tests unless a later registry revision allocates a byte-exact parser profile.
Before RFC 6901 selection, KAT JSON uses one strict deterministic parser:
exact UTF-8 without a BOM, Unicode scalar strings without normalization,
duplicate-name rejection at every depth, and finite binary64 numbers that
round-trip through the pinned JCS number serialization. Parser-dependent
first/last-wins or numeric coercion cannot establish evidence.

Only an `executable` evidence class invokes a module. KAT, schema-only, and
documented-nonwire vectors perform only their respective authenticated
source/contract, schema, or documentation checks; they do not imply a missing
producer or consumer execution. Only executable or independently sourced
known-answer evidence establishes semantic or cryptographic conformance, and
schema-only/documented-nonwire evidence never establishes wire behavior.

## Consequences

### Positive

- Normative bytes and prose agree before the 0.5.0 family is released.
- Security behavior moves out of non-normative generator code.
- KEL and consumer verdicts have an oracle independent of vector generation.
- Feature ownership and prerequisites become machine-checkable.
- Permanent credential-node loss has an explicit, auditable recovery path.
- Clients present Tier 3 and cold-root risks honestly.

### Negative

- Correcting 0.5.0 bytes changes event IDs, signatures, Git object IDs, and
  coverage digests.
- Registry revision 4 and manifest-schema changes touch every document
  release artifact.
- Emergency ledger reset deliberately invalidates usable credentials and
  requires reissuance.
- ATProto conformance is unavailable to browser environments that cannot
  control or observe the actual connection address.

## Alternatives considered

### Preserve invalid vector IDs and add replacements

Rejected. The existing vectors would remain normative contradictions. The
pre-1.0 mutability rule permits direct correction.

### Drop `repo_head` from the advertisement proof

Rejected. ADR-026 explicitly requires proof of repository possession over the
issuance-time canonical head.

### Permit witness-free `none` and choose a zero-threshold tie-break

Rejected. It preserves unilateral hot-key rotation and gives a compromised
epoch key avoidable authority.

### Canonicalize DEFLATE by recompressing

Rejected. Draft-21 does not define one canonical compressed byte form, and
local recompression breaks interoperable signed tokens.

### Hash public Tier 3 recipients

Rejected. A recipient does not yet possess the audience key needed to derive
the proposed hash, and stable hashes remain correlatable.

### Complete Control and MLS as part of remediation

Rejected. Both are separately gated features, not regressions introduced by
the reviewed changes.

## Conformance impact

This ADR changes normative 0.5.0 bytes, registry contents, release manifests,
reason precedence, and security validation. Corresponding vectors are
mandatory. The complete test and vector requirements are in the linked design
record. They include no-dependency routine rotation/addition/removal positives
whose mandatory config-row successor changes `K(C)` and the governed-binding
digest while heads, bindings, and obligations remain byte-identical, plus
rejection of a stale predecessor governed-binding digest across that inventory
change. They also cover the parentless-`B`/direct-child-`T` carrier with
logically ordered `K`/`R`/`O`/dependent proofs/transition co-committed
independently of lexical tree order, and reject a new transition-bound proof
in `B`, incomplete proof bytes before transition signing, an intermediate
commit, or any dependency on `T`'s commit OID.
